Page 1 — High-level system design

Everything owns one job.

MockX is assembled from a small set of intentionally narrow components, each with a single responsibility. The lifecycle coordinator serializes all state transitions. The scheduler maintains simulated time. The engine owns the books and matching. The gateway bridges FIX to the internal domain, while the optional ITCH publisher consumes the engine's authoritative displayed-order stream. The optional GLIMPSE service captures recovery snapshots at the same sequence boundary.

1.1

The exchange is a directed graph of ownership, not a bag of services. MockExchange (in main.py) holds the top-level references; each component receives only the dependencies it needs.

1.2

Exchange lifecycle

The exchange has five explicit states. Every state mutation is serialized through one asyncio.Lock in ExchangeLifecycle. Click each state to see its behavior.

STOPPED Initial / after end
STARTING Resetting run state
ACTIVE Accepting traffic
RUN_FAILED Metrics lost; rerun required
ENDING Flushing & finalizing
FAILED Unrecoverable error

STOPPED

No simulation session is active. Administrative start is available. FIX application ingress and time advancement are rejected.

Session start flow

Flush inactive metrics → close WebSockets → reset engine/scheduler/sequences/RNG → increment generation → install fresh run identifiers → start a fresh ITCH/Mold session and enable its GLIMPSE snapshot generation when configured → publish ACTIVE. Resume pending FIX delivery records from previous generations. Market-data socket failure degrades only that feed; destructive core failure → FAILED.

Session end flow

Idempotent when no session is active. GLIMPSE revokes the ending generation before a coherent ITCH feed publishes end markers and Mold end-of-session. Returns only current-run business metrics. FIX delivery records remain frozen while STOPPED, then reschedule at next start.

Publishing STARTING or ENDING accepts the transition. Its owned task keeps the lifecycle lock until completion, even if the caller is canceled repeatedly; cancellation propagates afterward. Cancellation before acceptance does not start a transition or cancel pending final broadcasts. Internally interrupted writes retain their records for retry. Lifecycle states and transitions: lifecycle.py. Scheduler state is a separate SchedulerState contract. Gating logic: ingress rejected with Business Message Reject (35=j) during STARTING/ENDING/STOPPED/RUN_FAILED/FAILED.
1.3

Two clocks, one purpose each

MockX strictly separates simulated time (the domain clock that determines event ordering, fill timestamps, and report scheduling) from monotonic real time (used only to measure how long actual matching computation took on the CPU). The two clocks never share a metric or influence each other.

Simulated clock

A datetime stored on LatencyScheduler.current_time. Advanced explicitly by advance_time() or run_until() in external mode, or by a background asyncio task in realtime mode. All order timestamps, fill timestamps, report timestamps, and event scheduling use this clock. Never calls sleep().

latency.py — LatencyScheduler.current_time, advance_time(), run_until()

Monotonic clock

Backed by time.perf_counter_ns() via PerfCounterClock. Used exclusively for real CPU duration measurements: match loop, book commit, engine command, report creation, and FIX serialization. Exposed as microsecond Prometheus histograms (e.g. mockx_match_loop_duration_us). Never influences event ordering or simulated timestamps.

latency.py — PerfCounterClock, monotonic_duration_ns()

external mode

Nothing advances time automatically. A test harness or admin endpoint calls run_until() / advance_time() explicitly. An entire trading day replays faster than reading this sentence. Events exactly at the advancement target are processed (inclusive).

realtime mode

A background task wakes every scheduler.interval_ms and calls run_until(current + interval_ms). Simulated time tracks wall time closely enough for live FIX sessions. Manual advancement returns HTTP 409 CLOCK_MODE_CONFLICT.

1.4

FIX ingress: from wire to scheduler

QuickFIX callbacks for New Order Single (35=D) and Order Cancel Request (35=F) parse immutable normalized command data only — they never touch the engine. A central run-scoped ingress sequencer timestamps and acknowledges each command, then drains envelopes in a deterministic four-key order.

1
QuickFIX callback fires → ParsedFixCommand is built. Only MsgType, ClOrdID, Symbol, Side, OrderQty, Price, TimeInForce, OrigClOrdID are extracted. gateway.py FIXApplication.onMessage()
2
Normalization → OrderNormalizer converts decimal strings to integer ticks/lots using the instrument catalog. Rejects OFF_TICK_PRICE, OFF_LOT_QUANTITY, PRICE_NOT_ALLOWED, unsupported types. Returns FixIngressEnvelope. validation.py
3
Ingress sequencer assigns run-local ingress_sequence, simulated_receive_timestamp, and run_generation. The envelope's ordering_key is:
(simulated_receive_timestamp, SessionID, MsgSeqNum, ingress_sequence)
4
Sorted drain → Envelopes are consumed in ascending ordering_key order. New orders become new_order_received scheduler events; cancels become cancel_received events. gateway.py — FIXApplication.drain_ingress_locked()
5
Scheduler FIFO preserves causal ordering among later equal-time stages. The ingress sequence is the final tie-break, never the sole FIFO source. It resets to zero on every successful simulation start.

Why four keys?

Two commands from the same session with the same receive timestamp and different MsgSeqNum values keep their wire order. Two commands from different sessions at the same timestamp cannot depend on each other, but the stable SessionID comparison ensures deterministic replay.

Ingress barrier

Callers must await fix_app.wait_for_ingress() before advancing time. The returned IngressBarrier identifies the active run generation and captured high-water sequence, guaranteeing those commands entered the scheduler before time moves.

FixIngressEnvelope and IngressBarrier: models.py. Sorted drain: gateway.py.
1.5

Run generation and public identifiers

Every successful simulation session start increments a run generation counter. All public identifiers embed this generation, making it impossible to confuse a trade from run 3 with a trade from run 7.

FIX / public fieldFormatInternal counter source
OrderIDG{generation:08d}-O{counter:08d}identifier_scope.next_order_id()
ExecIDG{generation:08d}-E{counter:08d}identifier_scope.next_exec_id()
TradeIDG{generation:08d}-T{counter:08d}identifier_scope.next_trade_id()
Cancel Reject IDG{generation:08d}-R{counter:08d}identifier_scope.next_cancel_reject_id()
FIX Delivery IDG{generation:08d}-D{counter:08d}Application-internal only

Numeric engine handles remain internal to REST, FIX, and WebSocket contracts. Within one generation-qualified Mold session, ITCH deliberately uses the run-local numeric order ID as Order Reference Number and trade ID as Match Number. The cancel-reject domain ID is an application identity for deduplication and observability — FIX OrderCancelReject (35=9) has no ExecID, so the domain ID is not serialized on the wire.

RunIdentifierScope: identifiers.py. MatchingEngine.identifier_scope: engine.py. Readme section: "Public exchange identifiers include the successful simulation-run generation."
1.6

API surface comparison

MockX exposes four distinct interfaces, each with a different contract.

FIX 4.4

Native order entry

New Order Single (35=D) and Order Cancel Request (35=F). Execution Reports (35=8) and Order Cancel Rejects (35=9) are delivered asynchronously through the reliable application delivery queue. Market Data Request (35=V) is rejected — market data is served by REST/WebSocket.

REST

Administration & submission

POST /api/v1/orders for REST order entry. GET /book/{symbol} for immutable snapshots. POST /api/v1/session/start and /end for simulation control. POST /admin/advance-time for clock advancement. GET /stats and /metrics for observability.

WebSocket

Streaming market data

Connect to /ws/{symbol}. First message is the current immutable snapshot. Every committed matching action publishes one market_data message with incremental trades. Heartbeats are distinct. Global per-exchange sequence incremented per publication.

ITCH 5.0

Displayed-order multicast

Optional downstream-only MoldUDP64 feed. Publishes A, one passive-side E/C per fill, and D, plus session/directory/trading-state messages. One internal lot is one ITCH share. No retransmission service is provided.

GLIMPSE 5.0

Atomic snapshot recovery

Optional SoupBinTCP service. Sequence-1 logins receive R, current H/T, every live resting order as A, and final G with the Mold next-message sequence. Interrupted spins are replayable within strict TTL/session/byte bounds.
