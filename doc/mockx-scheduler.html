Page 3 — Scheduler, timing, and delivery

Events never sleep.

The LatencyScheduler is a discrete-event simulator backed by a min-heap ordered by (timestamp, sequence). Nothing calls sleep(). Work is scheduled forward in simulated milliseconds and revealed by advancing the simulated clock — externally or in real time.

Speed

Sequence tie-breaking

Two events at the exact same simulated millisecond execute in the order they were queued — the sequence field breaks the tie. Passive then aggressor FIX delivery records retain engine order, and a same-time ITCH heartbeat is deterministic.

Inclusive advancement

run_until(target_time) processes all events with timestamp ≤ target_time. An event at exactly T+15 fires when you advance to T+15. The simulated clock stops at the target after the loop.

ScheduledEvent: models.py (scheduled event dataclass). Queue structure and heap operations: LatencyScheduler in latency.py. Event model: ScheduledEvent in models.py.

3.3

Cancel scheduling: a four-stage pipeline

Cancels are more complex than new orders. They pass through four scheduled stages before delivery, plus the cancel_received ingress event.

cancel_received T+0 Ingress sequencer → scheduler
cancel_arrived_at_exchange T+inbound session + inbound latency
cancel_engine_process T+inbound+engine calls cancel_order()
fix_delivery_due T+inbound+engine+outbound eligible for FIX send
delivered ~T+total transport send attempt
StageEvent typeWhat happens
1 cancel_received Envelope drained from ingress queue, enters scheduler. Observability only.
2 cancel_arrived_at_exchange Applied inbound latency. Marks arrival for latency tracking. No book mutation.
3 cancel_engine_process Calls engine.cancel_order(). Resolves against authoritative state. Produces CANCELLED report or CancelReject.
4 fix_delivery_due Report or reject enters the outbound FIX delivery queue. Applies outbound latency before becoming eligible for transport send.

Cancel vs. match race

Equal-time events keep scheduler priority. A queued match can fill an order before a later cancel fires, returning TOO_LATE_TO_CANCEL. Conversely, a cancel wins only when its engine event fires first. No implicit ordering guarantees exist — it depends on configured timings and the explicit ingress/scheduler ordering.

Version guard

A successful cancel increments order.version. Any already-queued stale order_process carrying the old version is a no-op. There's no need to dequeue or cancel the old event.

Cancel scheduling: LatencyScheduler.schedule_cancel_processing(). Full contract: README “Deterministic FIX ingress and cancel latency”.
3.4

FIX delivery: reliable application queue

Execution Reports and Order Cancel Rejects enter a process-lifetime application queue with five explicit states. The queue survives simulation session resets — records from a previous run are rescheduled at the next start.

PENDING
DUE
DELIVERED
RETRY PENDING
PERMANENTLY FAILED

PENDING

Record created but not yet due. Waiting for outbound latency to expire.

FIFO per session

Only the oldest non-delivered record for a stable FIX session may be submitted. A blocked session never prevents another session from progressing. Per-session ClOrdID history survives reset.

Retry and pruning

Transport failures retry at fix.delivery_retry_interval_ms with bounded attempts per cycle. DELIVERED records are capped at delivery_terminal_retention_records (default 10,000). PENDING, DUE, RETRY_PENDING, and PERMANENTLY_FAILED records are never pruned.

FixDeliveryState: models.py. OutboundFixDeliveryQueue: delivery.py. Full specification: README “Reliable FIX application delivery”.
3.5

Fail-stop: no silent failures

An unexpected event-handler exception is fatal. The scheduler immediately enters FAILED state. The offending event is removed from the live queue into an immutable dead-letter record. Later events remain queued but are never processed. Nothing is silently retried or dropped.

Once FAILED:
  • Scheduling new events → raises SchedulerFailedError
  • Processing the queue → raises SchedulerFailedError
  • Advancing time → raises SchedulerFailedError
  • POST /admin/advance-time → HTTP 503 SCHEDULER_FAILED
  • /readyz → HTTP 503 with components.scheduler="failed"
  • /stats → still available for inspection of dead letter

Failure triggers

Three causes:
1. Handler exception — any unhandled Python exception in an event handler.
2. Missing handler — no registered handler for the event type.
3. Processing limit exceeded — max_events_per_advance (100,000 by default) surpassed in one advance.

Dead letter contents

The dead letter captures: event_id, event_type, scheduled_timestamp, scheduler_sequence, exception_type, exception_message, and immutable event_metadata. Never includes the live mutable payload object.

Failure state: LatencyScheduler._fail_event(). Dead letter: SchedulerFailure dataclass in models.py. SchedulerFailureStatus: models.py. Processing limit: DEFAULT_MAX_EVENTS_PER_ADVANCE in latency.py.
3.6

WebSocket market data streaming

Each committed matching action publishes one immutable market_data snapshot to all subscribers of that symbol. The snapshot contains current bid/ask levels and incremental trades from that specific matching action.

1
Client connects to /ws/{symbol}. Validated symbol, lifecycle-gated.
2
Initial snapshot — current immutable book state with empty trades array, using latest published sequence (not incremented).
3
Matching action — engine._send_market_data_update() creates a snapshot with only the fills from that action in the trades array. Global sequence incremented once.
4
Fan-out — snapshot is pinned into each subscriber's bounded outbound queue. At most one later unsent snapshot retained (conflation). Heartbeats are distinct messages that do not advance the sequence.
5
Slow client protection — blocked socket cannot delay another symbol or client. Queue full → oldest pending snapshot dropped. 5-second send timeout → client disconnected with code 1013.
WebSocket registry: websocket_delivery.py. Market data snapshot creation: MatchingEngine._send_market_data_update(). Full specification: README “WebSocket protocol”.
3.7

ITCH and MoldUDP64 delivery

The optional publisher is owned by MockExchange and starts one fresh downstream session per run. It receives only the engine's authoritative displayed-order events; it does not infer book state from FIX reports or duplicate the book in a cache.

Engine commit time

A / E-or-C / D

Displayed events publish immediately after successful mutation and invariant validation. Each fill maps to one passive-side execution using the engine trade ID as Match Number.

Message sequence

Advance by Message Count

A data packet carries the sequence of its first message and advances by its count. Heartbeat count 0 and end count 0xffff carry the current next sequence without consuming it.

Idle heartbeat

Scheduler-qualified

itch_heartbeat contains the run generation. An interval containing data suppresses its heartbeat; an idle interval sends one and schedules the next check.

Publisher: itch_delivery.py. Encoder: itch_encoder.py. Packetization and socket ownership: moldudp64_transport.py. This is downstream-only; request and retransmission service are not implemented. Field layouts and packet semantics follow the official TotalView-ITCH 5.0 and MoldUDP64 specifications.
3.8

GLIMPSE and SoupBinTCP recovery

The optional process-lifetime listener supplies a point-in-time resting book that is synchronized to the existing run-scoped ITCH sequence. Snapshot copying is lifecycle-serialized; encoding and TCP delivery are not.

Atomic cut

Book plus next ITCH sequence

The lifecycle validates every book and copies FIFO order scalars together with the Mold next-message sequence. The final G tells clients which buffered ITCH message to apply first.

Sequenced spin

R / H / A / G

Soup sequence 1 starts directories, current trading actions, all live resting orders at leaves quantity, and the end marker. Every higher-level message has its own Soup S envelope.

Backpressure

Bounded and isolated

Per-connection writes have timeouts. Interrupted immutable spins are replayed by named session within strict TTL, session-count, connection-count, and byte limits; no client I/O holds the lifecycle lock.

Service: glimpse_service.py. Snapshot encoder: glimpse_encoder.py. Framing and fixed fields: soupbintcp_transport.py. The current state model emits only R, H/T, unattributed A, and final G.
